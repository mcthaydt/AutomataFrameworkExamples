# The Showcase Demo (Plan D) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task, in
> one session per part, with no subagents (project rule). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The demo game grows from one room with two boxes into the showcase the M2 spec asks for: one short real game
of three levels, about five minutes from the title screen to the last door, that shows every core feature of the
framework to anyone who plays it, on a phone first.

**Architecture:** The game stays what it is today: files under `content/` that `automata.toml` lists, a thin page
(`src/features/play/`) and a few sim rules of its own, importing only the published package. It grows in ten parts,
each its own pull request that starts by moving the framework pin. A part starts only when the framework plan it uses
is merged to the framework's `main`; five parts can be planned in full today and five wait on work that is not built
yet, and say so. The hero's movement and controls leave the game's code for content (the built-in hero); the game's own
code is only its rules (the door, the sparks, keeping players together) and its page.

**Tech Stack:** what the repo has, plus three font packages the first spec names (Part 1). No other new dependency.

**Spec:** [`2026-11-14-m2-design.md`](https://github.com/mcthaydt/AutomataFramework/blob/main/docs/superpowers/specs/2026-11-14-m2-design.md)
("The demo game as showcase", "Plans", "Testing", "Done means"), with its addenda
[`2026-11-14-content-hero-controls-design.md`](https://github.com/mcthaydt/AutomataFramework/blob/main/docs/superpowers/specs/2026-11-14-content-hero-controls-design.md)
(the built-in hero and the thumb scheme),
[`2026-11-14-no-default-language-design.md`](https://github.com/mcthaydt/AutomataFramework/blob/main/docs/superpowers/specs/2026-11-14-no-default-language-design.md)
and [`2026-11-14-watch-mode-design.md`](https://github.com/mcthaydt/AutomataFramework/blob/main/docs/superpowers/specs/2026-11-14-watch-mode-design.md),
all in AutomataFramework. Each framework plan's "Plan D's step" section is this plan's input and is named where it is
used.

**Principles served:** 1, agent-first (every level, sound, word, number and picture of the demo is a documented file
an agent can change; the game's code holds only rules); 3, layers in order (2D in full before anything else); 4,
separate repos (the game uses only the published package); 5, the builders carry over (the demo's art is made with the
figure builder and the environment builder); and the onboarding rule (a first-time player learns what to do, how, and
that they did it).

## Global Constraints

- **Only the published package.** `src/` imports `@automataframework/framework` and
  `@automataframework/framework/headless` and nothing else. `tests/architecture.test.ts` holds it.
- **Nothing runs locally** (the Owner, 2026-11-14): no test, lint, typecheck, build or generator. Every "Push" step
  below is verified in the pull request's GitHub-hosted CI, read with `gh` or the GitHub tools. A red step is pushed
  first where the task says so.
- **The pin is a commit on the framework's `main`**, never a branch, in `dependencies` and in
  `pnpm.onlyBuiltDependencies`, with the lockfile (a lockfile-only `pnpm install --lockfile-only` is allowed for this).
  Each part's first commit is the pin move alone, and CI is green on it before anything else is pushed.
- **Content has one writer.** Every content file is committed as `writeContent` writes it (`pnpm content:write`).
- **Goldens.** `replays/level-1.json` and `replays/test-game.json` are goldens, and this plan adds
  `replays/level-2.json`, `replays/level-3.json` and `replays/co-op.json`. Each is recorded in CI, never typed: delete
  the file, push, and commit what the Node job prints ("REPLAY NOT RECORDED. Commit this as ..."). A golden moves only
  in a commit whose message names the file and says why, and the part's report gives the Owner the old and the new
  final hash and what a player would see differ.
- **Mobile first** (the Owner, 2026-11-14): design and test at `phone-390x844` first, then the other four sizes of
  `tests/journeys/open.ts` (`phone-844x390`, `tablet-820x1180`, `tablet-1180x820`, `desktop-1280x720`). Input priority
  is touch, then gamepad, then keyboard. Touch targets are at least 44 px, primary actions 48 px.
- **The look.** The game's own screens use the Blueprint look in palette No. 340 from
  `src/features/play/blueprint.css` and nowhere else; a touch control is chalk at rest and Peach Red `#f15a30` while
  held; the one font is Fredoka with its partners (Part 1), never under 18 px. The game's art is in palette No. 276
  (Black `#111314`, Seashell Pink `#fdd4bd`, Yellow Green `#afd472`, Eosine Pink `#f37f94`). No sentence names a colour.
- **No default language.** Nothing a player reads is written in code. Every such word is in `content/messages/` in
  English (US), Spanish (Mexico), Korean, Japanese, Chinese and Portuguese (Brazil). The three sentences the page says
  before any file has loaded stay in code, for the developer, as the template has them.
- **The drunk-grandma test** for every word and screen. A screen that fails it is a defect.
- **Every part has an end-to-end journey** in Chromium, WebKit and Firefox, on the built page, and adds its pictures
  to `tests/journeys/pictures.journey.test.ts` at the five sizes.
- **No AI attribution**; author and committer McThayDT `<107786093+mcthaydt@users.noreply.github.com>`, set before
  every commit; the local hook that refuses any other author is installed before the first.
- **Never default on an Owner question.** Report it to the coordinator with options and wait.
- **Each part ends** by updating `docs/superpowers/progress.md` (Cycle 4, with a percentage), merging `main`, pushing,
  marking the pull request ready and reporting to the coordinator: one line per task (commit, test counts per job,
  surprises), each deviation with its reason, each golden's before and after, and where the pictures are.

## Review Focus

Five things the spec implies and no framework test covers, most likely first. Each has its test in the task named.

1. **A player leaves while the others stand in the door.** The level must finish for the players still in the game,
   and must not finish for nobody. Part 4, Task 4.2.
2. **An editor's save removes a level's door, or puts no start for a player.** The game must say which file and what
   to do, never open a level nobody can finish. Part 4, Task 4.3.
3. **The phone is turned, or the window resized, in the middle of a level or a conversation.** Nothing restarts, the
   hero is where it was, and the thumbs still work. Part 4, Task 4.6; Part 7.
4. **The browser refuses to store anything** (a private window). The game plays, says once in plain words that it
   cannot keep progress here, and "Continue" is not offered. Part 8, Task 8.4.
5. **A save names a level that is no longer in the game** (an editor renamed it). "Continue" opens the first level and
   says so, never a blank screen. Part 8, Task 8.4.

## My calls, for the audit and the Owner to overrule

The spec leaves these to the plan. None is an Owner decision already made.

- **What each level holds.** Level one (walk, jump): a ledge to jump, a crate to push into a gap, the keeper, the
  door. Level two (double jump): a wall too tall for one jump, the seesaw with a crate on it, three sparks, the
  critter. Level three (wall jump, then dash): a shaft to climb between two walls, a gap too wide to jump that a dash
  crosses, the swinging platform, the last door.
- **Level order is the order of the `level` blocks in `automata.toml`.** No new format; an agent reorders levels by
  moving a block.
- **"What's inside" is built from the messages files:** keys `inside.<feature>.what` and `inside.<feature>.where`,
  listed in the order the source language's file has them. A messages file is the only content kind that holds words,
  and a game cannot add a content kind.
- **Sparks are counted and shown, never required.** The door opens the level's end whatever the count; a player who
  misses a spark is not stuck.
- **A left-behind player is moved, not dragged:** see Task 4.2.

```ts
export const rulesPlugin: PluginDef       // name 'game.rules', dependsOn ['level', 'touch']
```

- `spark.taken` adds one to `sparks`.
- `door.touched` by a hero adds its player to `inDoor`; `door.left` removes it. Each tick `inDoor` is cut down to
  `playersIn(sim)`, so a player who left the game is not counted (plan P's handoff).
- The level is done on the first tick where `playersIn(sim)` is not empty and every one of them is in `inDoor`.
  `LevelDone` is emitted once, and `done` stays true.
- **Keep up** (only in a level with `view.most`, only with two or more heroes): when the heroes' spread sideways is
  more than `most.w - 2` tiles, the hero farthest from the middle of the others (on a tie, the higher player number)
  is put beside the hero nearest it, half a tile behind, at that hero's height, with no speed. The same for `most.h`.
  It is a rule in the sim, so it is in replays. It moves a body the way the pinned package gives for it; the tests fix
  the result and not the way.
